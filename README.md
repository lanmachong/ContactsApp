# 本地加密通讯录（ContactsApp）

一个**纯本地、无网络、无账号**的安卓应用。把手机通讯录、短信、通话记录搬进一个加密的本地库，
需要时再导回系统；配套来电识别悬浮窗，陌生号码也能看出是谁。

> 目标很朴素：**别让流氓软件读到你的联系人。** 系统通讯录、短信、通话记录对任何拿到权限的
> App 都是敞开的；搬进自己加密的库之后，那些 App 读到的只是一片空。

## 功能

| 功能 | 说明 |
| --- | --- |
| 通讯录备份 | 导入系统通讯录、加密入库、查看与拨号、CSV 备份 |
| 短信备份 | 导入系统短信、加密入库、查看全文、导出 CSV |
| 通话记录备份 | 导入系统通话记录、加密入库、查看号码时长、导出 CSV |
| 还原数据 | 把加密库写回手机系统：可多选内容、输确认词、写前先查重 || 清空数据 | 所有删除操作的唯一入口：可多选内容、选方向、输确认词 |
| 加密存储 | 整条记录 AES-256-GCM 加密，密钥由 Android Keystore 保管 |
| 来电识别 | 振铃时弹悬浮窗显示来电人姓名，只识别不拦截 |
| 重复标记 | 重复号码自动标记，搜号码即可定位 |
| 中英双语 | 界面文案随系统语言自动切换 |
| 纯本地 | 没有账号、没有服务器、没有埋点、不联网 |

### 三个备份页的界面骨架一致

「通讯录备份」「短信备份」「通话记录备份」三个页面共用同一套骨架，
读起来是同一个应用的三个模块，而不是三个拼凑出来的功能：

```
标题 + 「已加密保存 N 条/人」（真实总数，不是当前渲染的那一页）
  ↓
说明卡：这个功能在做什么、怎么保证安全
  ↓
统计条：系统里有多少 · 本应用里有多少
  ↓
主操作按钮：导入 / 导出 CSV
  ↓
提示卡：想把内容写回系统？到首页菜单的「还原数据」
  ↓
「已备份的 XXX」：列表 + 进度（已显示 200 / 共 12345 条）
  ↓
提示卡
```

**三个页面里都没有删除入口** —— 一条都没有，列表行里的垃圾桶图标也一并去掉了。
所有删除统一收在**首页右上角菜单 → 清空数据**；
所有写回系统统一收在**首页右上角菜单 → 还原数据**。


## 多语言

- 内置 **简体中文（默认）** 与 **English** 两套资源：`res/values/strings.xml` / `res/values-en/strings.xml`
- 跟随系统语言自动切换，App 内不提供手动切换入口 —— 需要换语言时改系统语言即可
- 构建时通过 `resourceConfigurations += listOf("zh", "en")` 只保留这两种语言，
  顺带剔掉 AndroidX 依赖自带的几十种翻译（打包语种从 74 个降到 2 个）

### 为什么中文要放两份目录

`res/values/` 是所有语言的兜底，`res/values-zh/` 是中文的 locale 限定副本，**两份内容必须一致**。

这不是冗余，是 Android 资源解析规则逼出来的：7.0+ 的系统会沿**用户的语言列表**逐个尝试，
而中文手机的语言列表通常是 `[zh-CN, en-US]`。只有 `values/` + `values-en/` 时，
查找顺序是 `zh-CN` → `zh`（无）→ 继续试 `en-US` → `en`（**有**），
于是中文系统反而命中英文，界面全变英文 —— 压根轮不到默认目录。

加上 `values-zh/` 后，`zh` 这一步就直接命中简体中文，问题消失。
详见 Android 官方文档 [Language and locale resolution overview](https://developer.android.com/guide/topics/resources/multilingual-support)。

改动文案后跑一次校验，防止三份资源键集合失同步（某个键漏了会在某个语种下静默串到另一语种）：

```bash
./verify-locales.sh
```

**写进数据库的文案不能跟着语言变**，否则用户切换语言后老数据会对不上：

| 数据 | 库里存什么 | 怎么显示 |
| --- | --- | --- |
| 「系统导入」分组 | 内部键 `__sys_import__` | 显示时经 `Labels.groupDisplay()` 翻译成当前语言 |
| 「重复」标记 | 独立布尔字段 `isDuplicate` | 显示时经 `R.string.tag_duplicate` 翻译 |
| 用户自己写的标签 / 分组 | 原样存储（属于用户数据，不该被翻译） | 原样显示 |

历史数据兼容：v1.3.0 存的是中文「系统导入」和混在标签里的「重复」，
`Labels.normalizeGroup()` 与 `Contact.fromJson()` 会在读取时自动识别并归一，
**老用户升级无需任何数据迁移**，分组筛选与重复检测照常工作。

## 加密设计

数据库 `contacts.db` 里每张表都只有两列：

```sql
contacts(id INTEGER PRIMARY KEY, payload BLOB)
sms(id      INTEGER PRIMARY KEY, payload BLOB)
call_log(id INTEGER PRIMARY KEY, payload BLOB)
```

`payload` 是整条记录 JSON 的密文：

```
[1 字节版本][12 字节随机 IV][密文 + 16 字节 GCM Tag]
```

也就是说，即使拿到 db 文件，也看不到任何姓名、号码、短信内容、备注，
**连字段名都没有**。解密密钥由系统 Keystore 生成，绑定设备，无法导出。

> 没有用 SQLCipher：它的 API 与系统 SQLite 不兼容、要求更高 compileSdk，且换来的
> 安全强度与「整行加密」相当（两者都保护数据文件，都不防已 root 且能调用 Keystore 的攻击者）。

### 两级密钥

- **联系人表**直接用 Keystore 里的主密钥加密。几百条数据，这个开销可以接受。
- **短信 / 通话记录表**走一层「会话密钥」：随机生成 32 字节软件密钥，用主密钥包裹后落盘，
  进程内解开放内存。原因是这两张表动辄几千上万条，逐条走硬件密钥会慢到十几秒。
  根信任始终在 Keystore —— 主密钥没了，落盘的会话密钥也解不开。

## 导入与清理的边界

- 枚举以 `Contacts` 表为驱动，`Phone` 表只用来补号码 —— 否则「只有姓名/邮箱、没有号码」的联系人会被整条漏掉，导致导入条数比系统里少、清理后还剩下这些人
- 导入时记录每个联系人名下**全部** `rawContactId`（一个人常由本机 + 云账号 + SIM 多条聚合而成，只记一条删不干净）
- 去重依据是 `rawContactId` 而不是号码，同号但是两条真实记录的不会被吞掉
- **重复导入不是跳过，而是比对更新**：系统里改了姓名或补了号码，再导入一次就能同步进库；以前直接跳过，导致「号码从姓名栏挪到电话栏」后库里那条永远是空的
- 同一 `rawContactId` 在库里出现多条（多次导入产生的副本）时，自动合并保留最新一条
- 姓名栏里误填成号码的脏数据，导入时自动把号码救回电话字段，否则按号码永远搜不到
- 号码搜索做了数字归一化：`+86 138-0013-8000`、`138 0013 8000`、`13800138000` 互相能搜到，后 7 位一致也算命中
- **清理 = 系统全量删除**：重复的、没有号码的、导入后新增的，一次清干净；删完回读实际人数，有残留自动再删一轮
- 提供 CSV 备份导出（明文，需自行保管）

### 清空数据：所有删除操作只有一个入口

删除动作原先散在四个地方（首页菜单、导入页第 4 步、短信页、通话记录页），
每处措辞不同、后果说明不同，用户很难判断自己删掉的到底是哪一份数据。
现在全部收进**首页右上角菜单 → 清空数据**：

- **先选方向**：清空系统里的原始数据，还是清空本应用里的加密副本
- **再勾选内容**：短信 / 通话记录 / 通讯录，可多选，**默认一个都不勾**
- **输入确认词**（中文「确认」/ 英文「CLEAR」）才允许执行 —— 删除不可撤销，值得多按一次键盘
- 执行时逐项独立处理，一项失败不影响其他项，最后汇总汇报每项删了多少、还剩多少

**方向决定了每项需要什么前置条件**，所以方向选择排在内容选择前面：

| 方向 | 可选内容 | 前置条件 |
| --- | --- | --- |
| 清空系统里的 | 三项都能勾 | 通讯录要 `WRITE_CONTACTS`；短信要本应用是「默认短信应用」；通话记录要 `WRITE_CALL_LOG` 运行时权限。条件没到位时页面先给提示和跳转按钮，真删不掉时回读条数、如实回报 |
| 清空本应用里的 | 三项全可选 | 删自己的加密副本不需要任何系统权限 |

三个备份页（通讯录备份 / 短信备份 / 通话记录备份）里**不再出现任何删除入口**，
连列表行里的垃圾桶图标也去掉了 —— 连「跳转过去」的入口都不留，
避免用户以为在备份页里点一下就删掉了什么。

### 删除短信为什么可能删不干净

**结论先说：剩下的短信大多是厂商私有库里的拦截消息，不是本应用故障，代码也补不了。**

这一节在 v1.8.3 / v1.8.4 里先后给过两套基于 AOSP 源码的推演，后来用
realme RMX3888（Android 16 / ColorOS）真机连 adb 只读核查，**两套推演都被推翻**。
以真机数据为准重写如下。

#### 真机看到的事实

| 查询 | 结果 |
| --- | --- |
| `content://sms`（含 `/inbox` `/all` `/sent` `/blocked` `/<单条 id>`） | 0 条 |
| `content://mms` | 0 条 |
| `content://mms-sms/conversations` | 14 行会话（9 个 `block_type=16` 拦截会话 + 5 个正常会话） |
| 骚扰拦截箱 | 用户实际看到几百上千条 |

`conversations` 的 SQL 里有 `GROUP BY thread_id HAVING date = MAX(date)` 和
`deleted = 0`，所以 14 是**会话数**而不是消息条数，不能拿来代表剩余总量。

#### 真正的原因

1. **骚扰拦截 / 垃圾短信 / 服务号卡片存在厂商私有库。** ColorOS 有独立的
   `com.oplus.communication.sms.interceptionProvider` 与 `mms-sms-local`
   （`com.oplus.mms.datamodel.MessageProvider`），访问都抛
   `SecurityException: requires com.oplus.permission.safe.MMS`。
   查权限定义：`sourcePackage=oplus, uid=1000, prot=signature|privileged` ——
   **厂商系统签名权限**，只授予 oplus 自己的系统应用，第三方 App 在清单里
   声明也不会被授予。「默认短信应用」角色只影响公共 `Telephony` Provider，
   跟私有库完全无关。
2. **各家 ROM 的标准不一样。** 有的完全隔离私有库，有的还会在非默认短信应用
   时把公共 `content://sms` 的查询整个过滤成空 Cursor（本机在默认角色已交还
   给 `com.android.mms` 后就是这样）。于是「软件显示系统短信 0 条」在
   **它可见的公共库范围内是真的**，但短信 App 把拦截箱合并展示给用户看，
   两边统计的根本不是同一个库。
3. **清空之后收到的新短信不会被追删**，这类即时验证码 / 取件码最容易撞上。
4. **只有默认短信应用能删公共库短信**；不是默认应用时系统直接拒绝。
5. **彩信在 `content://mms`，是另一张表。** v1.8.3 起两张表一起删、一起计数，
   这一处是有效的（真机上 4 条彩信确实被删掉了）。
   > ⚠️ 加密库只收文字短信，**彩信正文不会入库**，删前请先自行另存。

> v1.8.4 曾按 AOSP 源码推断「`sub_id = -1` 被订阅过滤挡住」，并改成逐条精确删。
> 在这台 ColorOS 上**不成立**：受限视图的过滤列表明确包含 `-1`，实际记录的
> sub_id 是 1 / 2 / 5 全为有效值；逐条删对私有库记录也没有对应的 `_id`。
> 该改动留着不影响正确性，但它不是这几条短信删不掉的原因。

#### 界面上怎么说明（v1.8.5）

清空页、还原页、短信备份页都加了 **VendorLimitNotice** 说明卡：明确写出
「不是软件故障、需要厂商系统签名权限、第三方应用拿不到、各家 ROM 规则不同、
统计条数只覆盖系统公共库」，并给出手动入口（ColorOS / MIUI / 鸿蒙 /
OriginOS 的「骚扰拦截 / 垃圾信息」名称各不相同）。清空结果弹窗也改成
如实说明，不再暗示「再清一次就能删掉」。

**手动清理**：短信 App → 骚扰拦截 / 垃圾信息 → 全选清空；建议关闭「智能识别
垃圾短信」或把取件码、验证码的发件号加白名单，否则拦截箱会持续收新消息。

> 附：v1.8.0 曾把「清空系统里的」下短信和通话记录一刀切禁用，理由「系统根本不放行」
> 对通话记录是**错的** —— `WRITE_CALL_LOG` 是可申请的运行时权限，v1.3.0 误判后
> 删掉声明才导致一直删不掉，v1.8.2 已恢复。v1.8.2 里手工拼的
> `content://sms/sub_id=<id>` 在 AOSP URI 表里不存在，v1.8.3 已移除。

### 大批量操作的进度与防中断（v1.8.5）

1w 多条数据时，备份 / 还原 / 清空 / CSV 导出会跑较久。v1.8.4 及以前只在
**首页**画了个小转圈，其他页面 busy 时仅有按钮变灰，看起来就是「点了没反应」。

v1.8.5 起统一由 `ContactsRoot` 挂一个全屏模态层 `BusyOverlay`：
独立 `Dialog` 窗口覆盖所有页面与弹窗，吃掉返回键和全部触摸，任务完成前
点不到软件其他地方；卡片里显示进度圈（有总量时带百分比）、当前阶段文字、
已处理 / 总数、**预计剩余倒计时**、已用时间，以及「请勿关闭软件 / 切后台 /
强制停止」的提醒。

进度是真实上报的，不是假动画：通讯录 / 短信 / 通话记录导入按条数上报，
清空 / 还原按分项上报，CSV 导出按分页回调上报。倒计时优先按实测速率外推
`（已用时间 × 剩余量 ÷ 已完成量）`，还没拿到进度时用调用方给的粗估时长
兜底并明确标注「仅供参考」，超出预估后如实改成「仍在处理，请继续等待」。
系统 Home 键与「强制停止」应用拦不住，所以提示里会写明别这么做。

### 系统权限的现实限制

Android 对这几个权限有硬性约束，代码里如实反映，不假装能删：

| 操作 | 权限 | 实际能否做到 |
| --- | --- | --- |
| 读通讯录 | `READ_CONTACTS` | ✅ 运行时授权即可 |
| 删通讯录 | `WRITE_CONTACTS` | ✅ 普通权限，授权即可 |
| 读短信 | `READ_SMS` | ✅ 运行时授权即可 |
| 写短信 | 本应用是「默认短信应用」 | ⚠️ 只读 `WRITE_SMS` 权限没用；不是默认应用时系统会静默丢弃写入 |
| 读通话记录 | `READ_CALL_LOG` | ✅ 运行时授权即可 |
| 删通话记录 | `WRITE_CALL_LOG` | ✅ CALL_LOG 权限组的 dangerous 运行时权限，声明 + 运行时申请后可删；个别 ROM 会拒绝，届时如实回报 |
| 写回通话记录 | CallLog Provider | ❌ 实测 `insert` 被系统拒绝，所以「还原数据」不提供这一项 —— 能删不等于能写回 |
| 读 / 删骚扰拦截箱 | 厂商系统签名权限（如 `com.oplus.permission.safe.MMS`） | ❌ signature\|privileged，只授予厂商系统应用；第三方声明也不授予，默认短信角色亦不附带。各家 ROM 规则不同 |

> 双卡与 `sub_id`：AOSP 源码里 `SmsProvider.delete()` 的 `SMS_ALL` 分支确实会
> 追加订阅过滤，但在真机 ColorOS 上这条路径被厂商定制的受限视图改写，
> 起决定作用的是「是否默认短信应用」和「记录是否在私有库」。
> 代码仍按 `sub_id` 分组回报剩余，便于定位，但不承诺能删掉私有库记录。

### 权限申请策略

原则：**按需申请、用完再撤，绝不一次性索要。**

- 启动时不申请任何权限，进入哪个功能才申请哪个功能需要的权限
- 通讯录的「读」和「写」拆开：导入只要读，还原/清空系统时才单独申请写
- 短信只主动申请「读」；`RECEIVE_SMS` / `RECEIVE_MMS` / `RECEIVE_WAP_PUSH`
  只在清单里声明，供系统校验「默认短信应用」资格，平时不申请、也不接收短信
- `WRITE_SMS` 同样只在清单里声明：它是系统授予默认短信应用角色时的伴随结果，
  **真正的门槛是角色本身**。判据只看 `isDefaultSmsApp`，不拿权限当拦截条件
- `WRITE_CALL_LOG` 恢复声明，且**只在勾选「清空系统通话记录」时**才运行时申请。
  Google Play 的上架政策要求「默认电话/短信/助理应用」才能申请这组权限，
  但那是审核规则，不是系统限制；本项目侧载分发，系统层面照常授予。
  个别 ROM 拒绝时按结果如实回报，不假装删掉了
- 需要切「默认短信应用」时，跳转做了三级兜底：
  Android 10+ 走 `RoleManager` 角色请求，9 及以下走 `ACTION_CHANGE_DEFAULT`，
  两者都失效时依次兜底到「系统默认应用页」和「应用详情页」，
  保证任何机型都能把用户带到能改设置的地方

未申请的权限清单：网络、位置、相机、麦克风、存储、通讯录以外的联系人读取 —— 一律没有。

## 重复联系人标记

- 判定同时覆盖两个来源：**系统通讯录里同一个号码出现在两个不同联系人上**，以及**本应用里同一号码出现多次**
- 命中的联系人自动打上重复标记。v1.4.0 起标记改用**独立布尔字段**（JSON 键 `isDuplicate`），
  不再混进 `tags` 文本 —— `tags` 是用户可以随便编辑的字段，把内部标记塞进去会在编辑页露出内部键，
  用户自己输入一个英文 "Duplicate" 也会被误判成系统标记
- 搜号码、搜「重复」都能定位到；系统通讯录里的重复卡片需要用户自己去系统里删 —— 本应用不替他改系统数据
- 入口：通讯录备份页的「检测重复」按钮；每次导入结束也会自动跑一遍。
  首页菜单里原本还有一个「检测重复联系人」的同名入口，v1.7.0 已收敛掉 —— 同一个功能不留两个入口。

## 还原数据：把加密库写回手机系统

原先「导出到系统通讯录」「导出到系统短信」分挂在通讯录备份页和短信页里，
用户不知道还有这么个能力，也容易在两个页面上找同一个功能。
v1.7.0 把写回系统这件事收进独立的**首页右上角菜单 → 还原数据**页，
与「清空数据」页互为镜像：一个往外删，一个往回写。

- **勾选要还原的内容**：通讯录 / 短信，可多选，**默认一个都不勾**
- **输入确认词**（中文「还原」/ 英文「RESTORE」）才允许执行 —— 写进系统同样值得多按一次键盘
- 执行时逐项独立处理，一项失败不影响其他项，最后汇总汇报每项写了多少、跳过多少、失败多少
- 写入前先比对系统里已有的内容并跳过，**不会把通讯录写成两份、短信写成两遍**
- 两个备份页里原来的写回入口改成一行提示，指向这里

写入能不能成功取决于系统权限，页面在勾选后就提前给出提示与跳转按钮：

| 还原内容 | 前置条件 | 实际能否做到 |
| --- | --- | --- |
| 通讯录 | `WRITE_CONTACTS` | ✅ 普通权限，授权即可 |
| 短信 | 本应用是「默认短信应用」 | ⚠️ 设为默认短信应用后才可写回 |

> 通话记录这一项 v1.8.0 撤掉后不再恢复：`WRITE_CALL_LOG` 能删通话记录，
> 但 CallLog Provider 对**新增**记录有额外限制，实测 `insert` 被系统拒绝。
> 放一个必然失败的选项让人点，不如不放 —— 清空页仍保留通话记录这一项。

### 短信还原为什么以前会「报告成功却没写进去」

这是 v1.8.0 修掉的核心问题。症状是：还原弹窗说「短信：已写回系统 N 条」，
但用户去手机自带的短信应用里翻遍也找不到那几条短信。四个原因叠在一起：

1. **清单里一个短信组件都没声明 → 本应用永远当不了默认短信应用。**
   Android 10+ 授予「默认短信应用」角色时会逐项校验清单，四个组件缺一个，
   系统设置里就不会把本应用列进候选，身份也就永远拿不到。
   v1.8.0 补齐了：`SmsCompatReceiver`（收到短信写回短信库，不丢）、
   `WapPushReceiver`、`ComposeSmsActivity`（极简撰写界面）、
   `RespondViaMessageService`（快速回复转接）。
2. **Android 4.4 起，不是默认短信应用时 `insert` 不会报错。**
   它照样返回非 null 的 Uri，短信却根本不会进短信库 —— 典型的「静默失败」。
   所以判据从「有没有 `WRITE_SMS` 权限」改成「是不是默认短信应用」，
   不是就直接拒绝并说明，不再假装写成功。
3. **写回时沿用了导入时记下的旧 `thread_id`。**
   用户清空过系统短信之后，那些会话早就不存在了，短信被挂到一个「幽灵会话」上，
   会话列表里根本不显示。现在写回前先扫系统里**现存**的短信建立
   「号码 → 会话 id」映射，命中才写，查不到就不写这个字段，让系统自己归组。
4. **`ExportSummary.failed` 计数被丢掉了。**
   部分写入失败时报告里只字未提。现在失败条数如实写进结果弹窗。

另外补了两件事：写回后**按 id 回读校验**（确认这条真的落进了短信库，
而不是只相信 `insert` 的返回值），以及把 **`sub_id` 一起存取**——
双卡机上不带订阅信息，短信会落到另一张卡的分组里，用户在常用的那张卡上根本看不到。

### v1.8.1：为什么「默认短信应用」列表里没有本应用

补完四个组件后，真机上仍可能看不到本应用。原因不在组件数量，而在**声明的细节** ——
AOSP 的 `SmsApplication.getApplicationCollection()` 是系统筛候选的地方，
它按四条固定的 Intent 去查，`SmsApplicationData.isComplete()` 要求四项全部命中：

| # | 系统的查询方式 | 组件要怎么声明 |
| --- | --- | --- |
| 1 | `SMS_DELIVER` | receiver，且 `android:permission="BROADCAST_SMS"` |
| 2 | `WAP_PUSH_DELIVER` + `setDataAndType(null, "application/vnd.wap.mms-message")` | receiver 里**必须带这个 mimeType**，且声明 `BROADCAST_WAP_PUSH` |
| 3 | `RESPOND_VIA_MESSAGE` + `smsto:` | service，声明 `SEND_RESPOND_VIA_MESSAGE`，filter 支持 `smsto` |
| 4 | `ACTION_SENDTO` + `smsto:` | activity，filter 支持 `smsto` |

v1.8.0 漏了第 2 项的 mimeType 和第 3 项的 `smsto` scheme —— 组件类都在，
但系统那两条查询**匹配不上**，于是 `isComplete()` 为 false，
本应用从头到尾就没进过候选列表。v1.8.1 补齐这两处，
并按 Google 对短信应用的规范补声明 `RECEIVE_SMS` / `RECEIVE_MMS` / `RECEIVE_WAP_PUSH`
（只在清单里声明，平时不申请、不收短信）。

顺带把「能不能写回短信」的判据收敛成**只看是不是默认短信应用**：
`WRITE_SMS` 只是角色的伴随结果，个别 ROM 上 `checkSelfPermission` 仍可能返回 false，
拿它当拦截条件会把已经拿到身份的用户挡在门外。真写不进去时，
`SystemSms` 的**按 id 回读校验**会把失败条数如实写进结果弹窗。

#### 应用内自检

还原页勾了短信、却还不是默认短信应用时，会多出一张「默认短信应用里找不到本应用？」卡片。
点「检查资格」，会把上面四条查询原样跑一遍，逐项显示命中与否，并给结论：

- **有项没通过** → 声明没写全，装最新版重试（关于页可看版本号）
- **四项全齐、角色不可用** → 本机没提供 `ROLE_SMS`，多见于无通话功能的设备或定制 ROM
- **四项全齐、角色可用，但列表里仍然没有** → 多半是厂商 ROM 对默认短信应用设了白名单，
  **代码改不动**。这种情况下短信无法写回系统，建议改用 CSV 导出留档

这一步把「我们的问题」和「手机的限制」区分开，不用再对着一个空白列表猜。

### 默认短信应用：不会自动换回来，必须手动切回

「默认短信应用」是一个**持久角色**，不是一次性的临时授权：

- **不会**过几分钟自动交还，也没有超时机制；只有用户在系统设置里把默认应用改成别的，
  角色才会转移。
- **应用自己交还不了**。Android 没有 relinquish 角色的 API，
  `createRequestRoleIntent()` 只能请求「成为」默认应用，不能反向调用。
  所以 App 能做的只是把用户带到「设置 → 默认应用 → 短信」，由用户手动选回原来的应用。

不切回会怎样？分三层说清楚：

| 情况 | 结果 |
| --- | --- |
| 收到的**文字短信** | 由 `SmsCompatReceiver` 写回系统短信库，**内容不丢**，切回后原来的短信 App 能读到 |
| 新短信**通知** | 本应用不发通知，原来的短信 App 也不再是默认应用，所以不会有新短信提醒 —— 用户容易误以为「收不到短信」，其实是没提示 |
| **彩信 / RCS** | `WapPushReceiver` 只是为满足系统资格校验的占位声明，本应用不处理彩信，这部分可能收不到或显示不出来 |

因此 v1.8.2 在**还原页和清空页**顶部都放了常驻提醒卡（含一键跳转到系统默认应用页），
操作完成的弹窗也会再提醒一次。切回之后 `WRITE_SMS` 伴随能力一并消失，
届时无法再写回或清空系统短信；下次要操作，重新临时设为默认即可。

> 既然短信还原能成功，就说明默认短信角色已经生效 —— **清空系统短信同样可以了**，
> 两者依赖的是同一个身份。v1.8.0 把清空系统短信灰掉属于过度保守，v1.8.2 已放开。
> 注意清空系统短信会删掉系统里全部短信，包括刚还原回去的那些。

### 导出的和写回的都是全表，不是界面上那一页

短信 / 通话记录动辄上万条，界面上一次只渲染 200 条（分页加载，避免卡首屏）。
早期版本导出时直接把「当前加载的这一页」写进 CSV，界面显示已备份一万多条、
导出的文件里却只有 200 条 —— 备份名存实亡。

现在导出走 `CsvExporter`，直接遍历加密表的全部内容：

- **逐页解密、逐页写出**（每批 500 条），写完一页释放一页，不会把全表塞进内存
- 导出的条数与界面显示的总条数一致，导完弹窗里报的就是实际写出的条数
- 写回系统同样走全表遍历，不会只把第一页 200 条写回去；
  去重用的「系统已有内容」指纹集合**跨页共用一份**，否则同一条会被写两遍

## 启动性能

加密存储的固有代价：打开 App 必须逐条解密（几百条就是几百次硬件密钥操作）。

- `ContactsRepository` 加了**内存缓存 + 互斥加载**，冷启动只解密一次。原来 Application 的来电索引预热和 ViewModel 的列表刷新各解一遍，等于白等一倍
- 解密**并发执行**（8 路），比串行快 3～4 倍
- 短信 / 通话记录表走会话密钥（软件 AES-GCM），且**分页加载**（每页 200 条），几千条也不会卡住首屏
- Keystore 密钥在 `Application.onCreate` 就预热，和界面初始化并行
- 首屏在解密完成前显示「正在解密本地通讯录…」，而不是空白页
- `release` 变体开启了 R8 + 资源压缩，包体更小、冷启动更快，**建议装 release 包**

## 来电识别实现路径

| Android 版本 | 号码来源 | 需要的授权 |
| --- | --- | --- |
| 10+ | `CallScreeningService` | 授予「来电显示和骚扰拦截」角色 |
| 8.0–9 | `PhoneStateListener` | `READ_PHONE_STATE` |

悬浮窗本身用 `WindowManager` + `TYPE_APPLICATION_OVERLAY`，需要「显示在其他应用上层」权限。
卡片不可获得焦点，不会抢走系统来电界面的触控。挂断后由前台服务撤掉。

本应用**只识别、不拦截**：`onScreenCall` 始终放行，不静默、不拒接、不录音、不上传。

## 构建与分发

需要 JDK 17 + Android SDK 34。用 Android Studio 打开项目根目录即可直接构建。

命令行（**只出 release**）：

```bash
export JAVA_HOME="<你的 jdk-17 路径>"
export ANDROID_HOME="<你的 android sdk 路径>"

./gradlew assembleRelease lintRelease   # R8 压缩 + 静态检查
bash verify-locales.sh                 # 三语文案一致性
```

产物：`app/build/outputs/apk/release/app-release.apk`

> `release` 变体当前沿用 debug 签名，方便直接覆盖安装调试。正式分发前请换成自己的签名配置。

### 为什么不再生成 debug 包

`debug` 变体本身保留（Android Studio 里断点调试、看 logcat、跑单测要用），
但 v1.8.2 起**不再产出、也不再分发 debug APK**：

- 它是 `android:debuggable=true`，别人用 `adb run-as` 或调试工具就能读到应用私有目录，
  包括加密数据库文件 —— 对一个「防止被流氓软件读取」的 App 来说，反而削弱了安全性
- 没有 R8 压缩，体积约 15 MB，是 release（约 1 MB）的十几倍
- 调试签名与 release 不同，两者不能互相覆盖安装，普通用户装了容易混淆
- 最终用户只需要一个能直接安装的包，多一个只会让人不知道该装哪个

要做二次开发的话，在 Android Studio 里点 Run 会自动构建 debug 变体，
不需要预先生成 APK 文件。

## 首次使用流程

1. 打开 App → 右上角菜单 → **从系统通讯录导入** → 授予通讯录权限 → 开始导入
2. 导入完成后先 **导出 CSV 备份**，确认数据完整；重复联系人会自动带上「重复」标签
3. 需要还原时用右上角菜单的 **还原数据**；确认系统里不需要了，再用 **清空数据** 页选方向和要清的内容、输入确认词执行
4. 右上角菜单 → **短信备份** / **通话记录备份** → 授予对应权限 → 导入
5. 右上角菜单 → **来电识别悬浮窗** → 依次授予通知、悬浮窗、「来电显示和骚扰拦截」
6. 打开「开启来电识别」开关，用「预览悬浮窗效果」验证样式
